Conceptos y ejemplos

Reproducibilidad: npm ci usa el lockfile, no selecciona paquetes por estabilidad. global.json fija política de SDK con latestFeature y sin prereleases. postgres:17 permite cambios de parche.

docker compose -p slotengine-clean config --quiet
docker compose -p slotengine-clean up -d
docker compose -p slotengine-clean ps
docker compose -p slotengine-clean down

El nombre explícito evita reutilizar el proyecto original; el puerto publicado 5433 se dirige al 5432 interno. down conserva el volumen nombrado; no usar --volumes como mantenimiento rutinario.

Configuración: Next.js escucha normalmente en 3000 y consulta SLOTENGINE_API_URL/health desde el servidor. La plantilla pasó de 5080 a 5140. Sin variable, getApiHealth devuelve false; errores HTTP, timeout y falta de conexión convergen en el mismo indicador. La API aún no comprueba la base de datos.

Preguntas de repaso

  1. ¿Por qué npm ci y no una instalación que pueda cambiar el lockfile?
  2. ¿Por qué -p aunque cambie el directorio?
  3. ¿Qué ocurre si PostgreSQL está apagado?
  4. ¿Qué versión incluye git commit si editamos después de git add?
  5. ¿Qué diferencia hay entre una dependencia instalada y una vulnerable alcanzable?
Respuestas
  1. Instalación basada en lockfile sin actualizarlo; falla ante incompatibilidad.
  2. compose.yaml fija el nombre slotengine; -p lo sobrescribe.
  3. El indicador puede seguir disponible si /health responde bien.
  4. La versión del índice, salvo opciones especiales de commit.
  5. Instalación no demuestra ejecución del código vulnerable por entradas externas; investigar rutas reales.
