2. C# y pruebas automatizadas

Una prueba unitaria verifica una unidad aislada. Una prueba de integración verifica la interacción entre componentes. En SLOT-008 usamos WebApplicationFactory<Program> para iniciar la aplicación con TestServer y enviar peticiones HTTP sin levantar un servidor externo.

Arrange, Act, Assert (AAA)

// Ejemplo didáctico abreviado
// Arrange: configurar factory y cliente
// Act
using var response = await client.GetAsync("/health");
// Assert
Assert.Equal(HttpStatusCode.OK, response.StatusCode);
Assert.Equal("Healthy", await response.Content.ReadAsStringAsync());

[Fact] identifica una prueba xUnit. async Task permite esperar operaciones asíncronas; await espera el resultado sin bloquear el hilo de forma síncrona. using var libera recursos al finalizar el ámbito; una directiva using importa un namespace y no instala paquetes.

EndpointContrato validado
GET /healthHTTP 200 y cuerpo Healthy.
GET /api/v1HTTP 200, MediaType application/json y propiedades name=SlotEngine API, version=v1, status=running.

Validar status y tipo de contenido antes de parsear JSON permite diagnosticar mejor un fallo. Comparar propiedades JSON evita depender de espacios u orden. El cliente de pruebas usa una dirección HTTPS simulada y desactiva redirecciones automáticas; no demuestra TLS real.

Error aprendido: una prueba vacía o una prueba sin assertions significativas puede pasar sin validar nada. Se provocó un fallo aritmético deliberado para observar el código de salida y después se sustituyó la prueba por casos reales.

La opción combinada audita también paquetes indirectos, como Microsoft.OpenApi. Listar dependencias no equivale a auditar vulnerabilidades. El resultado depende de las fuentes y del conocimiento disponible.

4. Git y revisión

Working tree: archivos locales. Staging/index: cambios preparados. Commit: fotografía versionada. Una eliminación no preparada puede hacer que CI ejecute una prueba que localmente ya no existe.

En esta sesión se olvidó incluir la eliminación de UnitTest1.cs en el commit. Se registró mediante git rm --cached y se corrigió el commit local con amend antes de publicarlo. Amend cambia el hash; no reescribir historial compartido sin coordinación. git diff --cached --check detectó espacios finales en YAML, que se corrigieron antes del commit.

CRLF y LF son finales de línea; el aviso de normalización de Git no implica un fallo de compilación.

5. GitHub Actions, Bash y selección del SDK

Un workflow contiene jobs y steps. Un runner Ubuntu ejecuta las operaciones cuando un PR hacia main modifica rutas relevantes. contents: read aplica mínimo privilegio.

dotnet restore SlotEngine.slnx
dotnet build SlotEngine.slnx --no-restore --configuration Release
dotnet test SlotEngine.slnx --no-build --configuration Release

Restore resuelve dependencias; Build compila; Test ejecuta pruebas. Separar las fases facilita el diagnóstico y evita operaciones redundantes. --no-build implica --no-restore en dotnet test. Si se omite Release, el test normalmente busca los binarios Debug: en un runner limpio pueden no existir.

El problema del SDK 11

El PR #11 tenía CI verde pero dotnet --version devolvió 11.0.100. Instalar SDK 10 no garantiza seleccionarlo. TargetFramework net10.0 define el framework objetivo, no el SDK que compila.

{
  "sdk": {
    "version": "10.0.404",
    "rollForward": "latestFeature",
    "allowPrerelease": false
  }
}

latestFeature admite versiones iguales o superiores compatibles dentro de 10.0; no admite SDK 11. disable exige la versión exacta. La flexibilidad facilita actualizaciones, pero distintos equipos pueden seleccionar SDK compatibles diferentes. setup-dotnet lee global.json; el archivo también está en los path filters.

sdk_version=$(dotnet --version)
echo "SDK version .NET: $sdk_version"
if [[ "$sdk_version" != 10.0.* ]]; then
  echo "SDK version mismatch. Expected .NET SDK 10.0.x"
  exit 1
fi

El script captura la salida, comprueba el patrón y devuelve un código de error ante una desviación. La ejecución positiva fue verificada; el caso negativo es un ejercicio pendiente. Los logs permiten diagnosticar, pero mostrar información no equivale a validar. La protección de ramas y los checks requeridos deben configurarse para impedir merges con validaciones fallidas.

7. Autoevaluación

Responde antes de desplegar cada explicación.

1. ¿Por qué una prueba puede pasar sin verificar el contrato?Porque ejecutar código sin assertions relevantes no detecta desviaciones.
2. ¿Por qué probar en Release?Es la configuración destinada a distribución; pasar Debug no garantiza el mismo comportamiento.
3. ¿Qué ocurre si se usa --no-build con Debug después de compilar Release?Se buscan artefactos Debug, posiblemente inexistentes o antiguos; no se recompila.
4. ¿Por qué auditar transitivas?Una dependencia indirecta también puede introducir vulnerabilidades.
5. ¿Por qué el commit contenía tres pruebas mientras localmente corrían dos?La eliminación no estaba preparada en staging; el commit conservaba UnitTest1.cs.
6. ¿Por qué instalar SDK 10 no bastó?El selector de SDK pudo elegir el SDK 11 instalado; global.json limita la selección.
7. ¿Qué pasa si solamente está instalado SDK 11 con nuestra política?No hay SDK compatible; el comando falla antes de compilar.
8. ¿Qué controla latestFeature y qué sacrifica?Permite feature bands compatibles posteriores en 10.0; no garantiza versiones idénticas entre equipos.
9. ¿Qué diferencia hay entre imprimir una versión y validarla?Imprimirla puede devolver éxito aun siendo incorrecta; la condición devuelve un código de error.
10. ¿Un CI rojo impide siempre el merge?No. Se requieren reglas de protección o rulesets con checks obligatorios.
