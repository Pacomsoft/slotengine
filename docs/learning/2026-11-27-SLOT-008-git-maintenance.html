Git Repository Maintenance

Seguimiento de SLOT-008 · Sprint 0 · Refinamiento metodológico

Objetivo: gestionar ramas y evidencia de integración sin perder trabajo, y conectar el aprendizaje con prácticas colaborativas profesionales.

1. Evidencia y contexto

GitHub confirmó los PR #13 (bca50d1) y #14 (fb44bed) integrados. La terminal reportó main limpia y sincronizada, 13 → 1 ramas locales y 16 → 1 remotas tras la limpieza. No hubo nuevas pruebas de aplicación. La comprobación preventiva de cada rama no se realizó; no se acredita ausencia de commits únicos en todas ellas.

El modelo de formación incorpora análisis de problemas, arquitectura hexagonal dentro del monolito modular (propuesta pendiente de ADR), Enterprise Design Thinking, Scrum y evaluación adaptativa. No implica migrar a Azure DevOps ni adoptar Gitflow automáticamente.

2. Fundamentos y práctica

OperaciónPropósito y límites
git branch -vvRamas locales, último commit y upstream conocido; no consulta servidor.
git ls-remote --heads originConsulta directa de ramas reales remotas.
git branch -r -d origin/ramaElimina referencia local; fetch la recupera si sigue en servidor.
git push origin --delete ramaSolicita eliminar la rama del servidor; requiere permisos.
git fetch --pruneActualiza referencias y elimina las obsoletas; no borra ramas locales.
git branch -d rama / -DEliminación local con comprobación de integración / forzada. Verificar antes de forzar.
git diff main rama --statCompara árboles de contenido, no ascendencia.
git diff --checkBusca errores de whitespace y marcadores de conflicto introducidos; no demuestra igualdad.
git branch --merged mainComprueba alcanzabilidad histórica, no equivalencia tras squash.

Un PR abierto se actualiza con nuevos push a su rama. Un squash genera un nuevo commit que contiene los cambios netos, sin convertir los commits originales en ancestros. Amend reemplaza el commit y un push normal puede rechazarse por no ser fast-forward si ya se publicó. Preferir un nuevo commit correctivo en ramas compartidas.

Un archivo tracked no deja de serlo al añadirlo a .gitignore. git rm --cached ruta retira el archivo del índice y conserva la copia local. Un commit posterior no borra el contenido del historial previo; si se publicó información sensible, evaluar exposición y remediación específica.

3. Diagnóstico y decisiones

Incidente observado: se ejecutó branch -r -d y fetch recreó la referencia. Causa: se eliminó el puntero local, no la rama del servidor. La corrección fue push --delete, seguida de consulta remota y local.

Patrón recomendado: validación preventiva → ejecución → verificación posterior. Confirmar PR integrado, SHA final de origen y ausencia de trabajo posterior; luego eliminar ramas y comprobar main. Una comparación vacía prueba igualdad de contenido rastreado, no equivalencia de historial. Diferencias legítimas pueden existir si main avanzó.

Alternativas: interfaz GitHub o CLI, ambas válidas. Automatizar eliminación de ramas de origen elegibles tras merge y proteger main; configuración aún no verificada. GitHub Flow sigue siendo la base; Gitflow y trunk-based son alternativas a estudiar.

5. Repaso aplicado

  1. ¿Por qué fetch puede recuperar una referencia eliminada con branch -r -d?
  2. ¿Por qué --merged puede omitir una rama cuyo PR fue integrado por squash?
  3. Un PR fue aprobado y se publica un cambio posterior. ¿Qué controles revisarías?
  4. Un archivo privado ya fue publicado. ¿Basta con .gitignore?
  5. ¿Cómo verificarías una limpieza de ramas a escala sin confiar solamente en memoria?
  6. ¿Qué diferencia hay entre monolito modular y arquitectura hexagonal?
Respuestas y criterios de revisión
  1. La rama sigue en el servidor y fetch reconstruye el seguimiento.
  2. El squash no conserva los commits de origen como ancestros.
  3. Revisión del diff actualizado, checks, invalidación de aprobaciones según política y nueva aprobación cuando corresponda.
  4. No. Retirar seguimiento y evaluar historial y exposición; los datos ya publicados pueden persistir.
  5. Consultar PRs integrados y SHA de origen, comparar tips actuales, excluir ramas activas/protegidas y comprobar resultados.
  6. El monolito modular organiza módulos y despliegue; hexagonal aísla lógica de negocio de adaptadores externos.
